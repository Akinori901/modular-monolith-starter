# 00. 全体ルール（最優先・常時適用）

このリポジトリでコードを書くすべての作業者（人間・AI 問わず）に適用される。
**このファイルの規約は、他のどの指示よりも優先される。**

## このリポジトリの立場

**「レイヤード化できないフレームワークは諦める」ではない。切り方の軸が違うだけ。**

| | clean-arch-starter | 本リポジトリ |
|---|---|---|
| 対象 | 層で切れるフレームワーク | **層で切ると戦うことになるフレームワーク** |
| 切り方 | **層（水平）** | **機能パッケージ（垂直）** |
| 守るもの | 依存の**向き**（内側へのみ） | パッケージ間の**依存**と**公開面** |
| 破り方 | UseCase から Model を直接触る | 他パッケージの内部実装を直接触る |

**どちらも「規約を文章ではなく CI で落ちる形にする」点は同じ。**

Rails の ActiveRecord は「Model が永続化を知っている」前提の設計なので、
Repository 層を挟むとフレームワークと戦い続けることになる。
だから層ではなく**機能パッケージ**で切り、パッケージ間の依存と公開面を機械検証する。

→ 詳しい判断根拠は [docs/design-decision.md](../../docs/design-decision.md)

## 大原則

1. **パッケージ構造は規約である。** ファイルを「置きやすい場所」に置いてはならない。
   どのパッケージに属するかが決まらないファイルは、まだ設計が終わっていない。
2. **迷ったら CI に聞け。** 規約は文章ではなく、`make verify` が落ちるか否かで決まる。
   ローカルで `make verify` が通らないコードをコミットしない。
3. **規約を曲げるときは理由を残せ。** 例外そのものより、
   「なぜ曲げたか分からなくなること」が後で効く。
   `package_todo.yml` に登録し、理由をコメントで書く。

## AI 駆動開発での扱い

このリポジトリは AI にコードを書かせる前提で設計されている。
AI は「動くコード」を最短で書こうとするため、放っておくとパッケージ境界を貫通する。
それを防ぐのが `.claude/rules/` と CI の役割である。

- **実装前に、必ず該当スタックのルールファイルを読むこと。**
  - Rails を触る → `10-rails-modular.md`
  - インフラ/CD を触る → `40-infra-cd.md`
- **新しいファイルを作る前に、どのパッケージに属するか宣言すること。**
- **他パッケージの内部実装を直接呼ばない。** 公開 API（`app/public/`）だけを使う。
  「とりあえず動かす」ために内部を触れば動くが、それは CI で落ちる。落ちるのが正しい。
- **ルールを破る提案をされた場合、AI は実装せずに理由を提示して確認を取ること。**

### AI に対する検証の強制

`make verify` は以下を機械的に検証する。人間のレビューに依存しない。

| 対象 | ツール | 検証内容 |
|---|---|---|
| Rails | packwerk | パッケージ間の依存と公開面 |
| Rails | RuboCop | 静的解析 |
| Rails | RSpec | テスト |
| Rails | Brakeman | セキュリティ |

**どの検証も「違反を注入したら落ちること」を確認してある。**
落ちないルールは、書いていないのと同じ。

## 秘密情報

- **鍵・証明書・パスワードをコミットしない。** `.env` は `.env.example` のみ追跡する。
- AWS 認証情報はワークフロー内で **OIDC** により取得する。長期キーを置かない。
- ローカルのエミュレータの認証情報はダミー値のみ。

## コミット前チェックリスト

```bash
make verify      # パッケージ境界の検証 + 静的解析 + テスト
make fmt         # フォーマット
```
